- `api/utils/rate_limit.py` — `check_and_increment(key, limit, window_seconds)`. Redis `INCR`/`EXPIRE` counter, fails open. Used for per-user/per-tool limits on the AI assistant's agentic tool-execution path (bypasses Flask-Limiter since it calls service functions directly, not routes).
- `api/utils/usage_tracker.py` — `record_event(service, feature=None, user_id=None, input_tokens=None, output_tokens=None, status="success", ...)` writes one `ApiUsageEvent` row (fails open, never raises); `record_internal_api_call(endpoint, method, status_code, latency_ms)` is a Redis `HINCRBY` counter for internal API request volume, rolled into `ApiUsageHourly` by `tasks/usage_tasks.py::persist_hourly_usage_rollup` (hourly beat); `compute_anomalies(spike_multiplier)` flags any service whose last completed hour exceeds its trailing-7-day same-hour-of-day average — shared by both the `/api/admin/usage/summary` endpoint and `tasks/usage_tasks.py::detect_usage_anomaly`. Import from here rather than writing a second usage-tracking mechanism. `record_internal_api_call` no-ops when `current_app.testing` is true (Finding 2026-10-01, below) — `record_event` does **not** need this guard since it writes via `db.session`, which tests already isolate through `DATABASE_URL`; only the Redis-backed counter needed it, since `REDIS_URL` is shared with the real dev instance.
- `api/routes/usage.py` (`/api/admin/usage`) — API/token usage monitoring, gated by the shared `require_role("admin")` (admin + superadmin, same as every other route file — an older version of this doc incorrectly claimed a separate superadmin-only `_require_superadmin()` existed here; it never did, and the 2026-10-02 duplicate-code pass corrected both the code's local copy and this note). `api/models/usage.py` — `ApiUsageEvent`/`ApiUsageHourly`/`UsageAlertConfig`. `dashboard/pages/22_Usage_Monitoring.py` + `frontend/src/pages/UsageMonitoringPage.tsx` are the only UI surfaces gated to `role == "superadmin"` exactly (every other admin-ish page/nav-link accepts `admin` too) — that's a dashboard/frontend-only distinction, not an API-level one.
- `api/utils/ai_client.py` — `get_anthropic_client()`/`get_model(env_var, default)`. Shared Anthropic client constructor, used by both `routes/assistant.py` and `services/ticket_triage_service.py`. Extend from here, don't re-instantiate `anthropic.Anthropic(...)` inline a third time.
- `api/services/ticket_triage_service.py` — `run_triage(ticket_id)` (one forced `categorize_ticket` Claude tool call) / `apply_triage_decision(...)` (the server-side escalate/stage/auto-resolve gate — reads the `TriageCategory` row fresh in-transaction, never trusts the model's own `is_auto_resolvable`) / `danger_scan(text)` (reused by `routes/ticket_triage.py` to re-scan a human-edited `reply_override` before it's sent). `api/tasks/triage_tasks.py` — `triage_ticket` (on-demand, idempotent on `Ticket.triage_status`) / `auto_close_resolved_tickets` (hourly beat). Triggered from `services/ticket_service.py::create_ticket_service` — the single scheduling point every ticket-creation caller shares, so don't add a second `.delay()` call site elsewhere.
- `api/models/triage_category.py` — `TriageCategory`: the curated whitelist admins edit via `PUT /api/triage/categories/<id>` (`auto_resolve_enabled` + `shadow_mode` + `confidence_threshold`, DB-backed like `SLAPolicy` so it's editable at runtime). No row exists for `"other"` — it's the always-escalate catch-all handled in code, not a whitelist entry that could be flipped on by mistake.
